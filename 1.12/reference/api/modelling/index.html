    Modelling MDPs¶

    Everything you import when writing an MDP, a State class, or a policy. These names live in dynaplex.modelling. Event distributions and random number generation are on the distributions & randomness page; the language rules for compiled code are in the language reference.

    The MDP contract¶

    There is no universal state class in DynaPlex. Each MDP defines its own State: a plain dataclass holding exactly the quantities that describe the system between decisions, plus one required field, category, which tells the engine whether the state next expects an event or an action. For the airplane ticket MDP, that looks like:

    @dataclass(slots=True)
class State:
    remaining_days: int
    remaining_seats: int
    price_offered_per_seat: int
    category: StateCategory = StateCategory.AWAIT_EVENT

    In the signatures below, StateType is a type variable standing for whatever State class your MDP defines — MDPProtocol is generic in it. An MDP, then, is a class whose methods operate on that state: it creates one (get_initial_state) and modifies it in place (modify_state_with_event, modify_state_with_action, write_action_validity). A policy operates on the same State class, and this shared type is what ties them together: assert_policy_for_mdp lets the type checker verify that a policy's StateType matches its MDP's.

    What is a protocol, and why the assert_* functions?

    A protocol is Python's way of describing an interface by shape rather than by inheritance: any class that has the listed attributes and methods satisfies MDPProtocol — you never subclass it or import it into your model. That leaves one gap: nothing tells you when your class doesn't match, e.g. a misspelled method or a wrong signature. That is what assert_mdp and friends are for. They do nothing at runtime, but a call like assert_mdp(mdp) gives a type checker such as pyright a place to verify conformance, so pyright my_model.py reports exactly which member is missing or mistyped — before anything is run or compiled.

    MDPProtocol ¶

    Bases: Protocol[StateType, ContextType]

    The interface every DynaPlex MDP class implements.

    An MDP class provides two attributes — horizon_type and num_actions — and four methods operating on a user-defined State class: get_initial_state, modify_state_with_event, modify_state_with_action, and write_action_validity.

    This is a structural protocol: any class with these members satisfies it, no inheritance needed. Call assert_mdp on an instance to have the type checker verify conformance (a no-op at runtime).

    Example

    A minimal skeleton (see the tutorials for complete models):

    @const_dataclass(init=False, slots=True)
class MyMDP:
    horizon_type: HorizonType
    num_actions: int

    def get_initial_state(self, context: TrajectoryContext) -> MyState:
        ...

    def modify_state_with_event(
        self, state: MyState, context: TrajectoryContext
    ) -> None:
        ...

    def modify_state_with_action(
        self, state: MyState, context: TrajectoryContext, action: int
    ) -> None:
        ...

    def write_action_validity(self, state: MyState, valid: Validity) -> None:
        ...

assert_mdp(MyMDP(...))  # pyright verifies protocol conformance

    Policies: the two shapes¶

    A policy maps a decision state to an action index. DynaPlex recognizes exactly two get_action signatures and tells the policy kinds apart by shape:

    @const_dataclass
class GreedyPolicy:                    # deterministic — by construction
    mdp: MyMDP

    def get_action(self, state: MyState) -> int: ...

@const_dataclass
class NoisyPolicy:                     # context-driven
    mdp: MyMDP

    def get_action(self, state: MyState, context: TrajectoryContext) -> int: ...

    A policy with the (self, state) signature is deterministic by construction: it is never handed a source of randomness, so there is nothing it could draw from. Adding the second parameter — the exact name context with the exact annotation TrajectoryContext — makes the policy context-driven: the built-in algorithms (the comparer, DCL) pass the trajectory's context on every call. Through it the policy can use:

    • context.policy_rng — a random stream dedicated to policy draws, separate from the event stream and reseeded per trajectory from global coordinates. Results with a context-driven policy are therefore reproducible, independent of the number of worker threads, and safe for common-random-number comparisons.
    • context.valid — a reusable action-validity scratch (a ValidityWriter sized to the MDP's action space). Hand it to mdp.write_action_validity(state, context.valid) and read the mask back from it — no per-call allocation. It is overwritten on every use and carries no meaning between calls.

    The shape is validated before anything compiles or runs: exact parameter names, exact annotations, plain positional parameters, no defaults and no *args. Anything else is rejected with an error naming both accepted signatures.

    Rules a context-driven policy must follow

    The context also exposes trajectory state that a policy must leave alone. Draw only from context.policy_rng — never from context.rng, which is the MDP's event stream (touching it silently breaks common-random-number comparisons) — and never write context.cumulative_cost or context.time_elapsed. These rules are not yet enforced mechanically; today they are part of the contract.

    PolicyProtocol ¶

    Bases: Protocol[PolicyStateType]

    The interface every DynaPlex policy class implements.

    A policy provides one method: get_action(state) -> int, mapping a state awaiting a decision to the index of the chosen action. This is a structural protocol — no inheritance needed; call assert_policy_for_mdp to have the type checker verify that a policy fits an MDP (their State types must match).

    Example

    A minimal rule-based policy (see the tutorials for complete models):

    @const_dataclass
class ThresholdPolicy:
    mdp: MyMDP
    threshold: int

    def get_action(self, state: MyState) -> int:
        return 1 if state.inventory < self.threshold else 0

assert_policy_for_mdp(mdp, ThresholdPolicy(mdp, threshold=5))

    ContextPolicyProtocol ¶

    Bases: Protocol[PolicyStateType]

    The interface of a CONTEXT-DRIVEN DynaPlex policy.

    Identical to PolicyProtocol except that get_action receives a second argument: the trajectory's TrajectoryContext. Through it the policy may draw from the dedicated POLICY stream (context.policy_rng — independent of the event stream, so policy draws never perturb event draws and common-random-number comparisons across policies stay valid) and use the context's reusable action-validity scratch (context.valid, a ValidityWriter to hand to mdp.write_action_validity — no per-call allocation).

    The two signatures are how DynaPlex tells the policy kinds apart: a policy whose get_action takes (self, state) is deterministic BY CONSTRUCTION (it is never handed a source of randomness); adding the context: TrajectoryContext parameter — that exact name and annotation — makes it context-driven, and the built-in algorithms (PolicyComparer, DCL) hand it the per-trajectory context. The context's policy stream is reseeded per trajectory from global coordinates, so results stay reproducible and worker-count-invariant.

    Convention (not yet enforced): a policy must only use context.policy_rng for randomness — never context.rng, the event stream — and must not write context.cumulative_cost / context.time_elapsed. Mechanical validation of this contract is future work (roadmap mdp_validation_improvements).

    Example:

    ```python
@const_dataclass
class EpsilonGreedyPolicy:
    mdp: MyMDP
    eps: float

    def get_action(self, state: MyState, context: TrajectoryContext) -> int:
        if context.policy_rng.random() < self.eps:
            return context.policy_rng.choice(2)
        return 1 if state.inventory < 5 else 0
```

    States and trajectories¶

    StateCategory ¶

    Bases: Enum

    The category of a state, determining which operation runs next.

    Every DynaPlex state carries a category field of this type; the trajectory loop dispatches on it:

    • AWAIT_EVENT: a random event is next — modify_state_with_event runs
    • AWAIT_ACTION: a decision is next — the policy picks an action and modify_state_with_action runs
    • FINAL: terminal state (finite-horizon MDPs); the trajectory has ended

    HorizonType ¶

    Bases: Enum

    Horizon type determines whether the MDP has a finite or infinite horizon.

    • FINITE: Episodes naturally terminate (reach StateCategory.FINAL)
    • INFINITE: Episodes never naturally terminate (simulation must be limited externally)

    TrajectoryContext dataclass ¶

    TrajectoryContext(rng: Generator, policy_rng: Generator, cumulative_cost: float, time_elapsed: int, valid: ValidityWriter)

    Context information for a trajectory/episode.

    This is the standard trajectory context used by DynaPlex MDPs. Users can extend this class if they need additional trajectory-level statistics or state, but at minimum it must contain: - rng: Random number generator for sampling events - policy_rng: Random number generator for randomized policies - cumulative_cost: Running total of costs accumulated during the trajectory

    Construct fresh contexts with make_context(mdp, seed) rather than calling the constructor directly — the factory derives an independent stream for each generator from a single seed and sizes the validity scratch for the MDP's action space.

    make_context ¶

    make_context(mdp: 'MDPProtocol', seed: int, *, eval: bool = False, sample: int = 0, trajectory: int = 0) -> TrajectoryContext

    Build a fresh TrajectoryContext for mdp whose generators carry independent streams.

    The coordinates are those of combine_seeds: distinct (eval, seed, sample, trajectory) tuples yield non-overlapping streams by construction, and the event and policy generators get one stream each. The context's validity scratch is sized to mdp.num_actions. Plain CPython convenience — inside compiled kernels, construct once and use reseed_context per trajectory instead.

    reseed_context ¶

    reseed_context(ctx: TrajectoryContext, eval: int, global_seed: int, sample: int, trajectory: int) -> None

    Reset ctx in place for a fresh trajectory at the given seed coordinates.

    Reseeds both generators (each on its own stream) and zeroes cumulative_cost/time_elapsed. Allocation-free, and runs identically in CPython and compiled code — after this call the context is indistinguishable from make_context at the same coordinates. Argument order follows combine_seeds.

    Validity module-attribute ¶

    Validity = Annotated[_Validity, InterpreterImpl(ValidityWriter)]

    Annotation for the action-validity mask parameter of write_action_validity.

    The MDP method signature is def write_action_validity(self, state, valid: Validity) -> None; inside, mark allowed actions with valid.set(a, cond). At least one action must remain valid in every AWAIT_ACTION state.

    For a worked example (accept/reject constrained by remaining seats), see write_action_validity in the airplane tutorial code.

    Const classes and annotations¶

    Compiled DynaML code relies on a few concepts that standard Python has no syntax for — most importantly constness: MDP and policy objects are read-only during a trajectory, and marking their classes with @const_dataclass lets the compiler enforce and exploit that. Similarly, the compiler needs some information that ordinary annotations do not carry, such as the rank of a NumPy array field; the Rank, Array*D and ConstArray*D annotations supply it. The names below are the API for declaring all of this; what constness means inside compiled methods, and the rules for array dtypes and ranks, are explained in the language reference under const classes and read-only containers and NumPy arrays.

    const_dataclass ¶

    const_dataclass(_cls=None, **kwargs)

    Declare a read-only DynaML dataclass — the standard decorator for MDP and policy classes.

    Combines @dataclass with const marking: every instance of the decorated class (and everything reachable through its object-typed fields) is read-only in compiled DynaML code. This is the required convention for MDP and policy classes, whose self must not change during a trajectory: construct and fill the object in __init__ (plain CPython, unrestricted — load data, validate, precompute), and compiled methods then only read it.

    Accepts the same keyword arguments as @dataclass. The common form for an MDP is @const_dataclass(init=False, slots=True) with a hand-written __init__:

    Example 
    @const_dataclass(init=False, slots=True)
class MyMDP:
    num_actions: int
    demand_dist: DiscreteDist
    demand_sampler: AliasSampler

    def __init__(self, mean_demand: float):
        # plain CPython: unrestricted
        self.num_actions = 2
        self.demand_dist = DiscreteDist.poisson(mean_demand)
        self.demand_sampler = self.demand_dist.alias_sampler()

    Array1D module-attribute ¶

    Array1D: TypeAlias = Annotated[NDArray[_NDArrayScalar], Rank(1)]

    A 1-dimensional NumPy array annotation.

    In DynaML, every array annotation must fix both the number of dimensions and the element dtype: Array1D[np.float64] declares a 1-dimensional ndarray holding float64 values. The allowed dtypes are np.float64, np.float32, np.int64, and np.bool_. (Equivalent to Annotated[NDArray[np.float64], Rank(1)].)

    Copying state¶

    clone ¶

    clone — deep copy for branching (e.g. Sequential-Halving rollouts) — and clone_into — deep IN-PLACE assignment.

    clone(x) returns an independent, MUTABLE copy of x; everything DEEPLY const it reaches is SHARED (linked), not duplicated. A structurally-const list of MUTABLE-class elements is NOT deeply const: it is copied and its elements cloned (both here and in the interpreter). This is a real Python function (used when DynaML code runs in pure CPython) AND is recognized by the interpreter frontend as a builtin that lowers to the C++ clone opcode — the same dual role as sync_worlds.

    clone_into(src, dst) recursively overwrites dst's contents so it becomes value-equal to a deep copy of src, preserving dst's identity (objects, lists, ndarray backings) wherever structure matches. THIS function is the semantic spec the interpreter builtin is parity-tested against; it carries the same two-map algorithm as the C++ walker (memo on id(src) reproduces src-side sharing; consumed on id(dst) prevents a dst object already claimed at one position from being overwritten again from another). Same-store row reuse in the interpreter corresponds exactly to in-place mutation here.

    Const detection here is by explicit @const_dataclass (__dynapl_const__). The interpreter shares by the propagated const flag; the two differ only for a class that is const only by propagation (never decorated), and only in is-identity (value-equivalent, since const is immutable). The same identity-only caveat applies to deeply-const LISTS and const ndarray fields (no runtime const marker exists here, so the clone mirror copies them; the interpreter shares them — value-equivalent because they are immutable). DCL's shared immutable data is always explicitly const, so it is exact there. clone_into reads FIELD const-ness from the Annotated[..., Const()] hints, so its links are exact.

    clone ¶

    clone(x: _T) -> _T

    Deep-copy x: independent mutable copy, sharing const_dataclass subgraphs.

    Typed identity (clone(x) has the same static type as x) so type checkers keep the argument's type instead of collapsing to Any.

    clone_into ¶

    clone_into(src: _T" backlink-type="used-by" backlink-anchor="dynaplex.modelling.clone.clone_into" optional hover>_T, dst: _T) -> None

    Deep in-place assignment: overwrite dst so it becomes value-equal to a deep copy of src, preserving dst's identity wherever structure matches.

    Both arguments must be two instances of the same MUTABLE dataclass, or two lists of the same type. External aliases of reused dst sub-objects observe the new values (that is the defined semantics, not an accident); where structure mismatches (None flips, ndarray shape changes, aliasing duals) the affected position falls back to a fresh clone. Overlapping src/dst graphs are unsupported. clone_into(x, x) is a no-op. Returns None (unmistakably a mutation).

    Validating your model¶

    assert_mdp ¶

    assert_mdp(mdp: MDPProtocol[StateType, ContextType]) -> MDPProtocol[StateType, ContextType]

    Type assertion function for MDP protocol validation.

    This is a no-op function at runtime, but type checkers (like pyright) will verify that the provided MDP satisfies the MDPProtocol interface. The type checker automatically infers StateType and ContextType from the MDP's method signatures.

    This pattern enables static type checking of protocol conformance without runtime overhead. If the MDP doesn't satisfy the protocol, the type checker will report an error.

    assert_policy_for_mdp ¶

    assert_policy_for_mdp(mdp: MDPProtocol[StateType, ContextType], policy: PolicyProtocol[StateType]) -> PolicyProtocol[StateType]

    Type assertion function for validating policy compatibility with an MDP.

    This is a no-op function at runtime, but type checkers (like pyright) will verify that the policy's StateType matches the MDP's StateType. The type checker automatically infers StateType from both the policy's and MDP's method signatures and ensures they are compatible.

    This pattern enables static type checking of policy-MDP compatibility without runtime overhead. If the policy doesn't work with the MDP (different StateType), the type checker will report an error.

    		 required

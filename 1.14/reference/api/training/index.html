    Training policies¶

    Sample collection, training algorithms, featurizers, and the trained agents and networks they produce. Everything on this page is imported from the top-level dynaplex package, except the observation-spec vocabulary (TensorSpec, Dtype, and friends), which lives in dynaplex.modelling. For assessing the resulting policies, see evaluating policies.

    Sample collection and training¶

    DCL ¶

    DCL(mdp: MDPProtocol, policy: PolicyProtocol | ContextPolicyProtocol, *, features: type[Featurizer], n: int = 5000, m: int = 1000, h: int | None = None, gen0: 'Shape | None' = None, trained: 'Shape | None' = None, seed: int = 0, reduction_factor: int = 4, final_field: int = 5, network: 'Net | None' = None, train: dict | None = None, root: str = 'dynaplex_runs', workdir: str | None = None, keep_samples: str = 'all', verbose: bool = True, jit: bool | None = None, gc_threshold_bytes: int = 16 << 20, torch_threads: int | None = None, compile_agent: bool = False, steps_per_round: int = 0, machine: 'str | DclPlan | None' = 'auto', device: str | None = None, policy_binding: str | None = None, policy_precision: str | None = None, allow_mismatch: bool = False, checks: bool | Literal['rehearsal'] | None = None, warmup_time: int | None = None, restart_after: int = 0, sample_info: bool = False)

    The Deep Controlled Learning generation loop; see the module docstring.

    Construct around an (mdp, heuristic policy, featurizer) triple, then call run(generations=G). Collection and training internals are collect_samples and train_network, which stay public for ad-hoc use.

    Parameterize a DCL experiment. Construction is cheap and torch-free (torch loads on run()); it creates the workdir and its dcl.json config record, but collects and trains nothing until run().

    Parameters:

    Name Type Description Default
    mdp MDPProtocol

    The MDP instance to solve.

    		 required
    policy PolicyProtocol | ContextPolicyProtocol

    The generation-0 rollout policy (e.g. a heuristic benchmark policy). Generations >= 1 roll out the previously trained agent instead; the heuristic labels only generation 0.

    		 required
    features type[Featurizer]

    The featurizer class defining the state representation (written with @featurizer) — e.g. LostSalesFeaturizer.

    		 required
    n int

    Number of labeled samples to collect per generation (default 5000, the legacy N).

    		 5000
    m int

    Rollout replications per candidate action (any value; need not divide workers; default 1000, the legacy M).

    		 1000
    h int | None

    Rollout horizon. On finite-horizon MDPs a rollout ends at the horizon or at a FINAL state, whichever comes first. None (default) = the legacy H: 40 on a finite-horizon MDP, 256 on an infinite-horizon one.

    		 None
    machine 'str | DclPlan | None'

    The execution plan: two shapes (processes, engines, workers, slots — one for generation 0, one for the trained policy), the trained policy's device and policy binding, hand-engineered for a machine. "auto" (default) recognizes which plan this allocation IS — "laptop" (derived from this machine's cores and accelerator) on macOS and Windows; on Linux one of "gpu_h100" / "gpu_a100" and their _half / _quarter units or "genoa" — and never invents one: an unrecognized allocation raises MachineMismatchError up front rather than run slowly on a shape nobody tuned. Pass a plan name, a dynaplex.machine.DclPlan, or None = no plan, both shapes Shape.TRIVIAL (1 process, 1 engine, 1 worker, 512 slots, cpu) unless gen0 / trained say otherwise. At collection time the plan is VERIFIED against the allocation (allowed CPUs, visible GPUs) and refuses to run on less — "always get a full node". Both shapes are part of the experiment identity (per shape: controllers = processes * engines, slots_per_controller = workers * slots).

    		 'auto'
    gen0 'Shape | None'

    A dynaplex.Shape overlaid on the plan's generation-0 shape: every field set here replaces the plan's, every field left None keeps it (Shape(workers=8) changes the workers only). Generation 0 rolls out the heuristic in-machine, so its shape has no forward to place.

    		 None
    trained 'Shape | None'

    The same overlay for the shape generations >= 1 run, where the trained policy forwards on device.

    		 None
    device str | None

    Where generation >= 1 rollout agents forward ("cpu"/"cuda"/"mps"); default from the plan, else cpu. Training runs on the plan's training device (cluster GPU plans: the GPU; laptop: the cpu, faster for small nets at batch 64), or on device when that is given explicitly; train=dict(device=...) overrides either.

    		 None
    policy_binding str | None

    collect_samples policy binding for the agent ("auto"/"blocking"/"device"/"graph"); default from the plan, else auto.

    		 None
    policy_precision str | None

    precision of the agent's forward on a device binding ("fp32"/"tf32"/"fp16"/"bf16"); default from the plan, else fp32. Lower precision is faster for attention-sized networks and may change near-tie actions.

    		 None
    steps_per_round int

    Generation-0 schedule: decisions a worker takes on one rollout slot before moving to the next within a round (0, the default: run each rollout to its cutoff, depth-first; 1 = the pre-2026-09 breadth-first sweep). A throughput knob like workers/slots: same sample distribution, different concrete draw.

    		 0
    warmup_time int | None

    Periods each main trajectory runs under the generation's own rollout policy (the heuristic at generation 0, the trained agent after) before its first labeled state, so samples describe the policy's stationary behaviour rather than the modeller's startup transient (legacy L). None (default) = the legacy default: 100 on an infinite-horizon MDP, off on a finite one; 0 = off. Infinite-horizon MDPs only. Warm states are produced up front per controller — a short prologue of batched forwards on generations >= 1 — and every worker keeps a copy of that supply.

    		 None
    restart_after int

    Labels (samples) a main trajectory contributes before it is retired and its slot restarted on a fresh warm state (legacy reinitiate_counter; 0 = never, the default). A sample-diversity knob for slow-mixing systems. Counted in labels, not periods. Both knobs are part of the experiment identity when active.

    		 0
    sample_info bool

    Record every sample's provenance (controller, arms, warm-start origin, label index, time, rounds, row) as the SampleSet's info slab, for scripts/dcl_audit.py. Free when off (a static flag in the machine); not identity.

    		 False
    seed int

    Global experiment seed, covering collection and training.

    		 0
    reduction_factor int

    Cap on the per-round reduction factor of the sequential-halving tournament: the candidate field shrinks from |A| to final_field in the fewest rounds whose steady per-round factor stays <= reduction_factor.

    		 4
    final_field int

    Number of candidate actions in the tournament's final round. These finalists all receive the (equal, largest) per-action rollout budget, so their cost estimates carry full evidence; the best of them is the label. States with fewer than final_field admissible actions run a single full-budget round over all of them.

    		 5
    network 'Net | None'

    Network spec for the trained agents — a dynaplex.MLP(...) or dynaplex.Net(...) spec, not a live torch module (agent files must rebuild from importable code). Default: MLP with hidden layers (128, 128).

    		 None
    train dict | None

    Keyword arguments passed through to train_network (e.g. loss, epochs, batch_size, lr, patience) — the single source of truth for training options.

    		 None
    root str

    Parent directory under which the default workdir is derived.

    		 'dynaplex_runs'
    workdir str | None

    Experiment directory. None (default, recommended) derives {root}/{MDPClass}_{mdp_hash8}/exp_{exp_hash8} from structural hashes, so every distinct (MDP, config) pair gets its own directory by construction. Passing a directory uses exactly that path with no hashing — you then own uniqueness: two different experiments pointed at one directory mix artifacts, and resume will load the other experiment's generations.

    		 None
    keep_samples str

    Sample retention, applied after each generation trains: "all" keeps every samples_gen{g} directory, "last" keeps only the most recent generation's, "none" deletes each generation's samples as soon as they have been trained on. Deleted samples make samples() unavailable for those generations; agents are always kept.

    		 'all'
    verbose bool

    Print per-generation progress.

    		 True
    jit bool | None

    None (default) uses the JIT when available, True requires it, False always interprets.

    		 None
    checks bool | Literal['rehearsal'] | None

    Runtime checks in the compiled kernels, applied to the GENERATION-0 collection only. "rehearsal" (the default) runs that collection once CHECKED at a tiny budget before the fast collection; True = the generation-0 collection fully checked; False = fast, no rehearsal; None = the DYNAPLEX_CHECKS=0|1 environment override if set, else "rehearsal". Generations >= 1 always collect fast: the rehearsal exists to catch an unchecked model or featurizer fault, and one that the generation-0 rehearsal does not surface is unlikely to surface under a later policy either, while checking every generation would cost speed. A resumed run that skips generation 0 therefore never rehearses.

    		 None
    gc_threshold_bytes int

    Auto-GC trigger threshold for the worker worlds.

    		 16 << 20
    torch_threads int | None

    If set, torch.set_num_threads(torch_threads) before training and collection. Torch's default (all cores) measurably HURTS the per-round inference batches of generation >= 1 collection on big multi-socket machines — one socket's worth of threads is a good starting point (measured on 2x96-core Genoa: 96 threads beat 192 by 2.6x). With processes > 1 every child process applies it too (spawned children would otherwise default to torch's all-cores pool).

    		 None
    compile_agent bool

    torch.compile the rollout agent's forward before each generation >= 1 collection (one-time warmup of tens of seconds, then a measurably faster forward).

    		 False

    allow_mismatch: an existing workdir whose dcl.json describes a DIFFERENT experiment (other MDP, policy, featurizer, parameters, plan split, network or training settings) is refused with a WorkdirMismatchError listing the differences — resuming there would mix artifacts of two experiments. True proceeds anyway (deliberate reuse, e.g. timing a new plan on stored generation-0 samples); the record is left as written.

    torch_threads and compile_agent are PERFORMANCE knobs and are deliberately EXCLUDED from the experiment hash and dcl.json — the same experiment resumes under different perf settings. Compiled and eager forwards are bitwise-equal on CPU (measured); thread count is part of torch's per-(machine, build, device) reproducibility caveat (see NNAgent.to) — in principle a different thread count could flip a near-tie forward, exactly like moving devices.

    train ¶

    train() -> NNAgent

    Run the training loop; returns the BEST-evaluating agent (the final one when evaluation is unavailable). Artifacts land in self.workdir: best_agent/, final_agent/, checkpoint.pt, tensorboard/.

    A completed workdir (existing final_agent/) is NOT retrained: the stored agent is loaded and returned.

    PPOConfig dataclass ¶

    PPOConfig(minibatch_size: int, num_envs: int = 256, num_steps: int = 128, max_episode_steps: int | None = None, backend: str = 'auto', workers: int = 0, jit: bool | None = None, total_timesteps: int = 500000, update_epochs: int = 4, anneal_lr: bool = True, lr: float = 0.00025, gamma: float = 0.99, gae_lambda: float = 0.95, eps_clip: float = 0.2, vf_coef: float = 0.5, ent_coef: float = 0.01, max_grad_norm: float = 0.5, norm_adv: bool = True, clip_vloss: bool = True, target_kl: float | None = None, critic_hidden: tuple = (128, 128), eval_interval: int = 10, eval_trajectories: int = 256, device: str = 'cpu', compile_agent: bool = False, seed: int = 42)

    Configuration for dynaplex.PPO. Only minibatch_size is required.

    Batch sizing: one update batch is num_envs * num_steps (defaults: 256 * 128 = 32768). The engine env makes envs nearly free — per policy step the cost is one kernel round plus one batched forward, so hundreds to thousands of envs is the intended regime (the old num_envs=8 default was an artifact of the serial CPython adapter).

    GAE horizon: don't shrink num_steps to compensate for env count — with gamma=0.99 the effective horizon is ~100 steps, so num_steps of 64-128 is the floor for dense-reward MDPs.

    Large batches: at fixed total_timesteps, more envs means FEWER update iterations. Compensate with a higher lr and/or fewer update_epochs (measured on lost_sales: epochs 4 -> 1 more than doubles end-to-end steps/s), and raise total_timesteps rather than starving the update count.

    SampleSet ¶

    SampleSet(features: dict, mask, y, q_sum, z, q_count, manifest: dict, info=None)

    quality ¶

    save ¶

    Built-in policies¶

    RandomPolicy ¶

    Pick uniformly among the actions the MDP marks valid in the current state.

    Works for ANY MDP unchanged: each decision it obtains the action-validity mask from mdp.write_action_validity (via the context's reusable scratch, context.valid — no per-call allocation) and draws one of the valid actions uniformly from the trajectory's policy stream (context.policy_rng). Under the built-in algorithms the results are reproducible, worker-count-invariant, and safe for common-random-number comparisons.

    Typical use: a zero-knowledge generation-0 rollout policy for DCL when no domain heuristic is available (a sensible heuristic, when you have one, remains the better starting point), or a baseline in PolicyComparer runs.

    Example:

    ```python
from dynaplex.models import RandomPolicy

d = dp.DCL(mdp, RandomPolicy(mdp), features=MyFeaturizer, ...)
agents = d.run(generations=2)
```

    Construct with the MDP whose valid actions are to be sampled — only its num_actions attribute and write_action_validity method are used.

    Featurizers¶

    A featurizer turns a decision state into the tensors a network consumes. Its writer fields declare the representation and write_features fills one batch row through them; spec() declares the observation spec — a plain dict[str, TensorSpec], one named tensor per writer field, batch axis implicit. An observation batch is the matching dict of batched arrays (everything downstream — network factories, SampleSet slabs, gym observations — is keyed the same way). spec() is optional on the class: when omitted, @featurizer synthesizes one that sizes by counting on a probe state.

    Featurizer ¶

    Base class of every featurizer — subclass it, apply @featurizer above @dataclass(slots=True), declare mdp plus writer fields (all Final — a featurizer is bound once), and write write_features::

    @featurizer
@dataclass(slots=True)
class MyFeaturizer(Featurizer):
    mdp: Final[MyMDP]
    v: Final[GlobalStateWriter]

    def write_features(self, state: MyState) -> None:
        self.v.append(float(state.on_hand))

    The base carries no fields: it exists so type checkers know a featurizer class up front (the features= argument of DCL, PPO, VectorEnv and PolicyComparer is type[Featurizer]) and see the methods @featurizer synthesizes onto the subclass (bind/reset/finish/spec and the derived Holder). The stubs here are never compiled: the decorator always overrides them on the concrete class, and they raise if reached (a featurizer used without the decorator). Same shape as TrajectoryContext / @trajectory_context.

    bind ¶

    bind(h: Any) -> 'Featurizer'

    A NEW featurizer of this class whose writers write into holder h's arrays (this instance is the factory: same mdp, fresh writers). Replaces the old in-place install(h): writer fields are Final, so binding to a holder is construction, not mutation — fz = fz.bind(h).

    featurizer ¶

    featurizer(cls: type[_T]) -> type[_T]

    Class decorator (apply ABOVE @dataclass): derive the FeatureHolder class and synthesize the absent methods — the field-walk trio install/reset/finish (engine-compiled) plus spec (CPython-only, declaration-by-counting).

    Defined by its expansion: the result is exactly the equivalent hand-written desugared form. Hand-written methods are left untouched (the escape hatch); a hand-written install also takes over holder selection — its parameter annotation IS the holder (holder_from_featurizer reads it), so nothing is derived or attached in that case. Otherwise the derived holder is attached as cls.Holder (user convenience; dcl itself deduces via install's annotation).

    GlobalStateWriter module-attribute ¶

    GlobalStateWriter = FeatureWriter

    The observation spec¶

    TensorSpec dataclass ¶

    TensorSpec(dtype: Dtype, sample_shape: tuple)

    One named featurizer output tensor: element dtype + PER-SAMPLE shape. The batch axis is deliberately NOT part of the shape — it belongs to the bundle, not the tensors (one spec serves n_target, slot capacity and minibatch size alike; the allocator prepends it: slab = [B, *sample_shape]).

    Dtype ¶

    Bases: _enum.Enum

    Element type of a spec tensor — a CLOSED vocabulary (what the writers can produce), deliberately in the engine-registrable enum shape (direct Enum subclass, consecutive int values from 1 — ONNX TensorProto precedent) even though nothing engine-side reads it today. Serialize by NAME, never by value: values renumber when members are inserted; names are the format. Names match numpy's (np.dtype(d.name) works).

    feature_spec ¶

    feature_spec(features_cls, mdp) -> dict[str, TensorSpec]

    THE observation spec for (featurizer, mdp): what features_cls.spec() declares, keyed by writer field name. A spec is a plain dict — the same shape a network factory receives, the agent sidecar stores and the SampleSet manifest carries. Note num_actions is NOT part of it: input representation and action space are different concerns (factories take both, separately).

    GlobalStateCounter ¶

    GlobalStateCounter()

    Bases: FeatureWriter

    The counting twin of GlobalStateWriter — same write surface, but it only tracks how many values were written, never storing them. CPython-only (never compiled). It subclasses FeatureWriter purely so a counter can be assigned to a GlobalStateWriter field under a type checker (the written-out spec() idiom); it has no array, and the engine never sees one (writer kinds are matched by class identity, not isinstance).

    Writer/counter pairing is the auto-sizing mechanism: construct the featurizer with a counter in a writer field, run write_features on a probe state, and ask the counter for the field's TensorSpec via spec(). Later writer kinds add their own counters (ObjectWriter <-> ObjectCounter), each reporting its own spec, so spec synthesis never needs to know writer kinds.

    Usage

    counter = GlobalStateCounter() twin = FeaturizerCls(mdp=mdp, v=counter) # a counter stands in for the writer field twin.write_features(await_action_state) ts = counter.spec() # TensorSpec(Dtype.float32, (count,))

    Create a feature counter initialized to zero (no backing array).

    Agents and networks¶

    NNAgent ¶

    NNAgent(module: _tnn.Module, spec: dict, num_actions: int, featurizer: str, network: Net, info: dict | None = None)

    The trained bundle: featurizer reference + network + selection + frozen spec.

    Callable at three cuts
    • agent(states, mdp=mdp) — pure-CPython convenience: featurize + forward + masked argmax on ordinary state objects (the cheapest way to test an agent).
    • agent.activations(features) — training/diagnostics cut.
    • agent.act(features, mask) — the engine-loop cut (what the DCL gen>=1 loop and the comparer NN path call).

    to ¶

    to(device) -> 'NNAgent'

    Move the FORWARD to device ("mps"/"cuda"/"cpu") and return self. This is the lever for gen>=1 collection and comparer evaluation throughput — their per-round minibatched forwards run wherever the agent lives (inputs are moved per call; outputs come back as numpy). Note the reproducibility caveat: results are bit-reproducible per (machine, torch build, DEVICE) — a cpu run and an mps run of the same collection may differ in near-tie argmaxes.

    compile ¶

    compile(**kwargs) -> 'NNAgent'

    Wrap the forward in torch.compile and return self (chainable, like to). Opt-in: one-time warmup of tens of seconds buys a measurably faster CPU forward on big per-round batches (the gen>=1 collection regime), and the compiled forward is bitwise-equal to eager on CPU — the action stream does not change. Serialization is untouched (save stores the plain module); compiling is a process-local property, never part of the agent's identity. Idempotent: a second call (any kwargs) is a no-op.

    activations ¶

    activations(features: dict) -> np.ndarray

    feature bundle (dict keyed by tensor name) -> activations [B, A].

    act ¶

    act(features: dict, mask: np.ndarray) -> np.ndarray

    (features, mask) -> actions [B] — the boundary cut of both engine loops. Torch-side end to end (forward, masking, argmax): only the [B] action vector crosses back to numpy, never the [B, A] activations. Same selection rule as masked_argmax, guaranteed by construction (measured on the DVRP example: the numpy round-trip was a third of gen>=1 act() time).

    save ¶

    save(path: str) -> None

    Directory of weights.pt + agent.json; atomic tmp+rename, refuses an existing path (artifacts are immutable).

    MLP ¶

    MLP(hidden=(128, 128)) -> Net

    The default network: Net sugar for the built-in MLP factory.

    Net ¶

    Net(factory: str, **kwargs)

    Constructible network spec: importable factory path + JSON-able kwargs. The ONLY way to specify a network (live modules are rejected by design — agent files must rebuild on cold nodes from importable code).

    train_network ¶

    train_network(samples: SampleSet, *, network: Net | None = None, loss: str = 'ce', epochs: int = 1000, batch_size: int = 64, lr: float = 0.0001, patience: int = 10, val_fraction: float = 0.05, val_every: int = 5, seed: int = 0, device: str = 'cpu', features=None, verbose: bool = False, step: str = 'auto') -> NNAgent

    Train a network on a stored SampleSet; returns the NNAgent bundle.

    Standalone and engine-free: never touches states or MDPs. The featurizer identity comes from the SampleSet manifest (or pass features= to override with the class itself). Targets per loss are computed once in numpy (see the module docstring); the optimization is masked cross-entropy with Adam, deterministic in seed (per torch's per-build determinism caveats).

    Training regimen (the legacy PolicyTrainer recipe + the DCL paper's Table 1 — with ONE deliberate deviation: default lr is 1e-4 where legacy hardcoded 1e-3. 1e-3 diverged outright on the DVRP example while 1e-4 matched the Akkerman paper's own tuned value; the safe rate is the right default, easy problems just take a few more epochs under the same early stopping): one seeded shuffle, then a validation split of max(1, val_fractionn) samples; the TRAINING set is RESHUFFLED EVERY EPOCH (measured to matter); validation loss every val_every epochs (legacy: 5), the best-validation weights are checkpointed and RESTORED at the end; early stopping once the epochs since the last validation improvement EXCEED patience — legacy's rule, so with the defaults training stops after the third failed check, 15 epochs without improvement (epochs is the maximum). val_fraction=0 disables the split, best-weight tracking and early stopping (fixed epochs on all data). verbose prints a line at every validation — losses with the legacy 100exp(-loss) percentage — plus the estimated validation cost REGRET per period (mean of qbar[predicted] - qbar[best] from the SH-honest q record; partial-budget means for eliminated actions make it an estimate). step: "auto" (default: graph on cuda, eager elsewhere), "eager", or "graph" (cuda only): the whole minibatch step — gather into static buffers, forward, masked loss, backward, Adam — is captured ONCE as a CUDA graph and replayed per minibatch (one launch instead of ~30; at batch 64 the eager step is launch-bound at ~1 ms on an A100). Same regimen: same minibatches in the same order, the last partial batch of an epoch runs eagerly, the capture warm-up is undone in place so the first replay is the first Adam step from the initial weights. Measured on an A100 (150k samples, batch 64): 2.9 -> 0.46 s/epoch (128x128), 3.9 -> 0.62 (256x256); the weights are reproducible run to run but differ from eager's at rounding level (the captured kernels and the capturable optimizer round differently); validation losses agree to 3 decimals.
